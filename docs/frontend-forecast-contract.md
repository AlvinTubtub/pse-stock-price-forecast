# ForecastPH frontend forecast-data contract

This document describes the operational JSON generated by the current backend and consumed by the Next.js frontend. Generated JSON is the website's forecasting-data source of truth. Historical research documents under `docs/research-history/` are archival and are not part of this contract.

## Required output tree

```text
frontend/public/forecasts/
├── companies.json
├── dashboard.json
├── latest.json
├── metrics.json
├── company/
│   └── <SYMBOL>.json
└── history/
    └── <SYMBOL>.json
```

The configured universe currently contains 15 companies. A complete export therefore contains 34 JSON documents: four global files, 15 company files, and 15 history files.

`history/<SYMBOL>.json` remains required by the exporter and validation contract even though current application pages read OHLCV from `company/<SYMBOL>.json`.

## Naming conventions

```ts
type ModelId = "lag_reg" | "arima" | "lstm" | "naive";
type PrincipalModelId = "lag_reg" | "arima" | "lstm";
type PrincipalModelLabel = "Lag-Informed Regression" | "ARIMA" | "LSTM";
type EvaluationModelLabel = PrincipalModelLabel | "Naive baseline";
```

The three principal models are deployable and receive next-session forecasts. Naive is an evaluation benchmark only.

The naming layers are exact and case-sensitive:

| Model | Metric ID | Display/backtest label | `nextClose` key |
| --- | --- | --- | --- |
| Lag-Informed Regression | `lag_reg` | `Lag-Informed Regression` | `lag` |
| ARIMA | `arima` | `ARIMA` | `arima` |
| LSTM | `lstm` | `LSTM` | `lstm` |
| Naive benchmark | `naive` | `Naive baseline` | not applicable |

## Common scalar types

```ts
type DateOnly = string;    // canonical YYYY-MM-DD
type IsoDateTime = string; // ISO 8601 with an explicit timezone offset

interface ModelMetric {
  rmse: number;
  mae: number;
  mase: number;
  r2: number;
  ljung_box_pvalue?: number;
}

interface OhlcvPoint {
  date: DateOnly;
  open: number;
  high: number;
  low: number;
  close: number;
  volume: number;
}
```

All numbers must be finite JSON numbers. Do not emit `NaN`, infinity, numeric strings, blank values, or null in required numeric fields. Market-session dates must be unique and ascending. Display timestamps are generated with Asia/Manila compatibility.

## `companies.json`

```ts
interface CompanySummary {
  symbol: string;
  name: string;
  sector: string;
  latestClose: number;
  predictedClose: number;
  pctChange: number;
  direction: "bullish" | "bearish";
  bestModel: PrincipalModelLabel;
  forecastDate: DateOnly;
  confidence?: number;
}

type CompaniesJson = CompanySummary[];
```

Symbols must be uppercase and unique. `bestModel` is the lowest-RMSE principal model from the latest chronological evaluation. `predictedClose` is that model's current next-session forecast. Zero percentage change uses `bullish` to preserve the two-value direction contract.

Consumers include the Home page, Companies directory, Watchlist, Models page, company routing, and AI context.

## `dashboard.json`

```ts
interface DashboardJson {
  generatedAt: IsoDateTime;
  forecastDate: DateOnly;
  lastRunAt: IsoDateTime | null;
  status: string;
  totalCompanies: number;
  missingCompanies: string[];
  sectors: Array<{ name: string; count: number }>;
  marketSummary: {
    gainers: number;
    losers: number;
    unchanged: number;
  };
  topGainer: CompanySummary | null;
  topLoser: CompanySummary | null;
}
```

Sector and market-summary counts must each total `totalCompanies`. Top mover fields are null only when the matching gainer or loser group is empty. Home dashboard cards and general AI context consume this document.

## `latest.json`

```ts
interface LatestJson {
  generatedAt: IsoDateTime;
  forecastDate: DateOnly;
  lastRunAt: IsoDateTime | null;
  status: string;
}
```

This is the lightweight freshness/status record used by the Home page and operational AI context.

## `metrics.json`

```ts
interface MetricsJson {
  generatedAt: IsoDateTime;
  forecastDate: DateOnly;
  lastRunAt: IsoDateTime | null;
  status: string;
  aggregate: Record<EvaluationModelLabel, ModelMetric>;
  bestModel: EvaluationModelLabel;
  worstModel: EvaluationModelLabel;
  perCompany: Record<string, {
    metrics: Record<ModelId, ModelMetric>;
    bestModel: PrincipalModelLabel;
  }>;
  statisticalTests: {};
}
```

`perCompany` must contain every configured symbol and exactly four metric entries per symbol. Canonical backend metrics retain full precision; the frontend formats them for display.

`aggregate` contains one summary for each display label. `bestModel` and `worstModel` refer to that aggregate comparison. `statisticalTests` is an intentionally empty compatibility object; the operational training pipeline does not populate a statistical-inference lifecycle.

The Models page derives current principal-model RMSE wins, median comparisons, company rankings, and Naive-relative results from `perCompany`. The chatbot uses the same current operational data and does not load a separate study result.

## `company/<SYMBOL>.json`

```ts
interface CompanyDetailJson {
  symbol: string;
  name: string;
  sector: string;
  previousClose: number;
  predictedClose: number;
  pesoChange: number;
  pctChange: number;
  direction: "bullish" | "bearish";
  model: PrincipalModelLabel;
  confidence?: number;
  metrics: Record<ModelId, ModelMetric>;
  nextClose: {
    lag: number;
    arima: number;
    lstm: number;
  };
  ohlcv: OhlcvPoint[];
  backtestDates: DateOnly[];
  backtestActual: number[];
  backtestByModel: Record<EvaluationModelLabel, number[]>;
  productionBacktestDates: DateOnly[];
  productionBacktestActual: number[];
  productionBacktestByModel: Record<PrincipalModelLabel, number[]>;
  forecastDate: DateOnly;
  dataAsOf: DateOnly;
  inferenceAt: IsoDateTime;
  backtestMethodology: {
    source: string;
    alignment: string;
    window: 60;
  };
}
```

Required cross-field invariants:

- `previousClose` equals the final OHLCV Close.
- `dataAsOf` equals the final OHLCV date.
- `forecastDate` follows `dataAsOf` and is determined by the PSE trading calendar.
- `model` is one of the three principal display labels.
- `predictedClose` equals the selected model's value in `nextClose`.
- `pesoChange = predictedClose - previousClose`.
- `pctChange = pesoChange / previousClose * 100`.
- `metrics` contains `lag_reg`, `arima`, `lstm`, and `naive`.
- `nextClose` contains fresh finite forecasts from all three principal models.

Company pages consume every summary field, the OHLCV chart, the three next-session projections, evaluation metrics, the predicted-versus-actual chart, and forecast errors. AI company context also uses the most recent five evaluation rows.

## Backtest arrays

The base arrays contain exactly the latest 60 sessions from the genuine chronological out-of-sample evaluation:

```text
backtestDates[i]
backtestActual[i]
backtestByModel[model][i]
```

Every model series must have exactly 60 values. Dates are ascending, all arrays are index-aligned, and all four evaluation methods use the same target dates and actual values. The frontend does not perform a date join or repair malformed arrays.

The Predicted vs Actual chart consumes these values directly. Forecast Error Over Time calculates:

```text
error[i] = predicted[i] - actual[i]
```

Positive values indicate overprediction; negative values indicate underprediction.

The `productionBacktest*` arrays hold optional realized prospective forecasts for the three principal models. They must either all be empty or remain date/length aligned. When populated, the frontend appends them after the stored evaluation window and marks the first prospective date.

## Next-day predictions

The Next-Day Prediction chart draws exactly three branches from the last observed Close:

- `nextClose.lag`
- `nextClose.arima`
- `nextClose.lstm`

Naive is not a production forecast branch. All three values are required even when one principal model wins the evaluation ranking.

## `history/<SYMBOL>.json`

```ts
interface HistoryJson {
  symbol: string;
  ohlcv: OhlcvPoint[];
}
```

The OHLCV array must exactly match the corresponding company document. This directory contains price history, not cached model predictions. It remains part of the exporter and validation contract.

## Nullability and failure behavior

- `dashboard.topGainer`, `dashboard.topLoser`, and global `lastRunAt` fields are the only explicitly nullable contract fields.
- Required company dates, timestamps, prices, predictions, metrics, and arrays are non-null.
- Prospective backtest arrays may be empty but must be present.
- Frontend readers return `null` when a JSON document is missing or invalid; `getCompanies()` returns an empty array.
- The Models page renders an unavailable state if any configured company or required metric set is incomplete.

## Publication requirements

The exporter must:

1. build payloads only from validated raw history, new canonical OOS evaluation records, and current production inference;
2. generate all 34 operational documents together;
3. validate strict JSON and cross-file consistency before publication;
4. stage temporary files outside the destination tree;
5. atomically replace destinations; and
6. roll back already replaced files if publication fails.

The exporter must not read existing frontend numeric values as model input. The website must never receive a partially written operational dataset.
